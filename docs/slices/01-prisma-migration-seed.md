# Slice 01 — Prisma Initial Migration + Seed

> **Type:** Infra (API)
> **Priority:** P0 — blocks every other slice
> **Blocked by:** None

## 1. Context

`apps/api/prisma/schema.prisma` is complete and matches [`docs/04-data-model.md`](../04-data-model.md). There is no `migrations/` folder yet, and `prisma/seed.ts` does not exist. The Postgres `order_number_seq` sequence (referenced by [`Slice 13`](./13-order-creation-api.md) for `orderNumber` generation) does not exist either.

Without this slice, the API cannot run against a real database, no other slice can be verified end-to-end, and the Platform Admin account cannot exist.

## 2. Goal

Produce a deployable database state: the initial Prisma migration applied, the `order_number_seq` Postgres sequence created, the AppConfig defaults seeded, and one PLATFORM_ADMIN account in Supabase Auth + DB.

## 3. Files to Create / Modify

### Create
- `apps/api/prisma/migrations/<timestamp>_init/migration.sql` — generated by `npx prisma migrate dev --name init`, then manually edit to append `CREATE SEQUENCE IF NOT EXISTS order_number_seq START 1;` at the end of the SQL file
- `apps/api/prisma/seed.ts` — idempotent seed script

### Modify
- `apps/api/package.json` — add `"prisma": { "seed": "ts-node prisma/seed.ts" }` if not present; ensure `ts-node` and `@types/node` are in devDependencies

### Read first (no edits)
- `apps/api/prisma/schema.prisma`
- `apps/api/.env.example` (or wherever `ADMIN_EMAIL` / `ADMIN_PASSWORD` are documented)
- [`CLAUDE.md`](../../CLAUDE.md) — section "Environment Variables"

## 4. Implementation Rules

- **Idempotency:** seed must be safe to run multiple times. Use `upsert` for users, AppConfig rows, and sequence creation. Do not throw on existing rows.
- **Supabase Admin SDK** is the only way to create a Supabase Auth user. Use `createClient(SUPABASE_URL, SUPABASE_SERVICE_KEY)` then `supabase.auth.admin.createUser({...})`.
- **Mirror User row:** after Supabase Auth user is created (or found existing), upsert a `User` row in our DB using the Supabase user ID as `User.id`, with `role: PLATFORM_ADMIN`.
- **AppConfig defaults:** seed exactly these two rows — `{ key: 'LOW_BALANCE_THRESHOLD', value: '50' }` and `{ key: 'SLOT_DURATION_MINS', value: '30' }`.
- **Sequence creation:** prefer adding it to the generated migration SQL so it is applied with `prisma migrate deploy`. Falls back to `prisma.$executeRawUnsafe('CREATE SEQUENCE IF NOT EXISTS order_number_seq START 1;')` inside the seed script as a backup.
- Read env vars via `process.env.ADMIN_EMAIL` and `process.env.ADMIN_PASSWORD`. Throw a clear error if missing.

## 5. Edge Cases

- **Seed run twice:** second run must not throw, must not duplicate rows, must not reset AppConfig values that have been edited via admin UI.
- **PLATFORM_ADMIN already exists in Supabase Auth but not in our DB:** find the existing auth user by email, then upsert the mirror DB User row. Do not attempt to recreate the auth user.
- **AppConfig value already changed by admin:** seed should not overwrite. Use `upsert` with `where: { key }` and `update: {}` (no-op) so existing values stick.
- **Database is empty (first deploy):** all entities seeded fresh — must succeed.
- **Migration run against a populated dev DB:** initial migration may attempt to create existing tables. Acceptable to `prisma migrate reset` once in dev; production is always a fresh DB.

## 6. Test Cases

This slice is verified through migration + seed runs, not unit tests.

1. **Migration applies cleanly to empty DB.** `npx prisma migrate deploy` returns success on a fresh database.
2. **Sequence exists after migration.** `SELECT nextval('order_number_seq');` returns `1` on first call, `2` on second.
3. **Seed creates Platform Admin first run.** After running `npx prisma db seed`, a User row with `role = PLATFORM_ADMIN` exists; can log in via `POST /auth/login` using `ADMIN_EMAIL` + `ADMIN_PASSWORD`.
4. **Seed is idempotent.** Running seed twice does not throw and does not create a second PLATFORM_ADMIN.
5. **AppConfig defaults seeded.** Both `LOW_BALANCE_THRESHOLD=50` and `SLOT_DURATION_MINS=30` rows exist.
6. **AppConfig preservation.** If a value is manually edited then seed re-runs, the edited value remains.

## 8. Agent Instructions

1. **Read these first, in order:**
   - [`docs/04-data-model.md`](../04-data-model.md)
   - [`apps/api/prisma/schema.prisma`](../../apps/api/prisma/schema.prisma)
   - [`CLAUDE.md`](../../CLAUDE.md) — Environment Variables section
   - [`docs/CODING_STANDARDS.md`](../CODING_STANDARDS.md) — Prisma usage section
2. **Verify env vars exist** in `apps/api/.env` (or `.env.example`): `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`. If `.env.example` is missing them, add them.
3. **Generate the migration:** `cd apps/api && npx prisma migrate dev --name init`. Inspect the generated SQL.
4. **Manually edit the generated SQL** to append `CREATE SEQUENCE IF NOT EXISTS order_number_seq START 1;` as the last statement.
5. **Write `seed.ts`** following the rules above. Use Supabase Admin SDK to create the auth user, then upsert the mirror User row, then upsert the two AppConfig rows.
6. **Test idempotency:** run `npx prisma db seed` twice; confirm second run does not throw or duplicate.
7. **Do NOT commit** any `.env` file or credentials.
